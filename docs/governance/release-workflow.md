# 内容审核与发布流程

> **适用对象：** 仓库维护者和内容审阅者
> **状态：** 流程规范；不表示 GitBook 后台功能已经配置或启用

## 1. 接收变更

1. 确认 PR 聚焦单一主题，描述了变更范围和核验依据。
2. 新页面应使用 `templates/` 中对应模板，并保留可见的内容性质、适用范围、最后核验、贡献者和状态。
3. 根据内容风险安排审阅：普通文案可由一名维护者审阅；涉及费用、资格、健康、安全、纪律、版权或个人争议的内容，应至少增加一名了解该主题的核验者。

## 2. 内容审阅

按 `.github/PULL_REQUEST_TEMPLATE.md` 检查，并特别确认：

- 易变信息是否注明适用时间、对象和一手来源。
- 个人经验是否被清楚标识，结论是否超出证据范围。
- 页面是否泄露个人信息、账号凭据、内部材料或未经许可的群聊内容。
- 图片是否具有使用权、已脱敏、已压缩并包含合适的替代文本。
- 措辞是否尊重当事人，是否把批评限定在可验证的事实和流程。

证据不足但仍有参考价值的页面，应标记为“待核验”或“可能过时”，不能通过模糊措辞伪装成已确认事实。

## 3. 结构与链接审阅

- 新增、移动、重命名或删除页面时，检查 `SUMMARY.md` 是否同步。
- 确认相对链接从目标页面所在目录出发可以解析。
- 移动已发布页面时记录旧路径和新路径，并检查 GitBook 后台是否需要配置重定向。
- 目录调整应服务于读者查找，不要只为统一文件名制造大范围链接变更。

## 4. 预览与合并

普通贡献者不需要安装 Node.js、pnpm，也不需要在本地运行 HonKit。

1. 使用 GitHub Markdown 预览检查标题、列表、链接和图片。
2. 如果管理员已经提供 GitBook 变更预览，可额外检查桌面和移动端呈现；没有预览不能成为拒绝纯内容贡献的唯一理由。
3. 所有阻塞意见解决后，由维护者将 PR 合并到实际与 GitBook 同步的发布分支。默认分支可能是 `main`，但应以后台配置记录为准。

## 5. 合并后核对

如果 Git Sync 已由管理员配置：

1. 在 GitBook 后台确认最新提交完成同步且没有冲突或错误。
2. 打开受影响的已发布页面，抽查目录、链接、图片、替代文本和更新时间。
3. 若启用了页面反馈，在 Insights 中确认相关反馈入口仍正常，但不要为了验证而提交虚假反馈。

如果 Git Sync 尚未配置、状态未知或同步失败，应把 PR 视为“已合并但未确认发布”，记录负责人和后续动作，不能宣称线上已经更新。

## 6. 回退与更正

- 出现隐私泄露、侵权内容、危险指引或重大事实错误时，优先停止传播并用新的修复 PR 或可审计的 revert 提交回退。
- 不要重写共享分支历史来掩盖错误。即使页面已删除，Git 历史仍可能保留敏感内容；如涉及凭据或高风险隐私，应立即轮换凭据并联系仓库管理员按平台流程清理历史。
- 更正后更新页面的“最后核验”和“状态”，在 PR 中说明影响范围及是否需要重新检查 GitBook 发布结果。

## 7. 定期维护

建议维护者按学期检查课程与办事页面，并定期查看失效链接、标为“待核验/可能过时”的页面以及读者反馈。Insights 数据只用于发现内容缺口和排序维护优先级，不应用来识别或追踪个人。
